# 长期计划

> 依据：`docs/audit/A01..A14` 十四份审计报告（这些报告不进公开仓库，`.gitignore` 已排除）。
> 每条都标注了证据出处与验证方式。**没有证据支撑的条目不进这份清单。**

## 编排原则

1. **按文件不重叠分批**。上一轮四个 agent 同时改 `tmwindow.h` 导致一小时互相破坏编译，这次每个批次独占一组文件。
2. **每批独立可验证**。做完就重建 + selftest + 提交，不攒到最后。
3. **不接受"注释写了就算改了"**。这个项目历史上多次出现注释与代码矛盾（`perfpage.cpp:1505-1516` 同一段注释里"本次没做"与"已接线"并存），判据只能是代码 + 实测。
4. **无法在本机验证的条目标 SKIP**，不假装验过。

## 批次 1：高分屏适配（最高优先级）

**为什么优先**：用户的原始投诉里有「高分屏怪怪的」。三个文件里 `Scaled()` 调用数为 **0**，在 125%/150% 缩放下所有硬编码像素都不对。

| 文件 | 现状 | 任务 |
|---|---|---|
| `src/perfpage.cpp` | 0 处 `Scaled()` | 布局常量全部走 `Rpx()`/`Scaled()` |
| `src/pages_view.cpp` | 0 处 | 同上（列宽、行高、表头） |
| `src/tmwindow_paint.cpp` | 0 处 | 同上 |

**风险**：本机是 96 DPI，**改完在本机看不出差别**。验证必须靠：
- selftest 里断言 `Dpi()` 返回值和若干矩形的计算值
- 离屏截图在不同 `--dpi=` 参数下比对（如果 CLI 支持）
- 或由你在高分屏机器上看一眼

**验证缺口如实记录**：这是本计划里唯一"本机验不了"的批次。

## 批次 2：统一滚动 / 表头（用户明确建议过）

**用户原话**：「进程、详细信息、服务用的列表是三套组件，它们对滚动的处理全部不是一个逻辑」「建议重构这部分，用统一控件」。

**我的判断：不做整体重写。** 三个列表（3735 行）的差异主要在行模型、渲染方式、交互语义，强行合并会引入新 bug 且难以验证。改为**提取共用行为**：

| 提取目标 | 现状 |
|---|---|
| `ScrollState`（像素偏移 + 惯性 + 边界） | 三处各写一遍 |
| 表头绘制（含排序箭头） | 三处各写一遍 |
| 行裁剪（`IntersectClipRect`） | 上一轮才发现 `PaintRows` 完全没有 |

**验证**：selftest 已有 12 条滚动断言，提取后必须全部仍 PASS。

## 批次 4：曲线横轴与量程

| 项 | 问题 | 证据 |
|---|---|---|
| x 映射拉伸 | `px = plot.left + k*(pw-1)/(n-1)` 用已有点数，开屏第 2 秒 3 个点横跨整格，横向放大 30 倍 | A10 |

## 已知不做

- **整体 ListView 重写**：三套列表差异大于共性，风险高收益低。只提取共用行为。
- **WMI 路径**：实测 `MSFT_PhysicalDisk` 要 103.9 ms（p95 263 ms），是 IOCTL 的 4000 倍。
- **PDH 走 1Hz 路径**：冷启动 1.0~2.7 秒（perflib 初始化），首屏会空白一秒多。`IOCTL_DISK_PERFORMANCE` 没有这个问题。
