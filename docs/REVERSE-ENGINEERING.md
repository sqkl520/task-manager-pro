# 全页面逆向成果（2026-11-24）

> 详细报告在 `docs/audit/H0*.md`（47 份，1.8 MB，含本机路径等细节，**不进公开仓库**）。
> 本文只保留**可公开的结论**与**对我方实现的指导**。

## 背景

用户定位：**「我们是在原版的基础上优化的」**。
所以逆向的目的分两层：数据口径必须对齐原版（否则就是"数据与原版不一致"），
显示与交互可以在合理处优化。

方法：对 `taskmgr.exe` 做静态反汇编 + PE 解析 + 只读探针。
**没有源码可读**（任务管理器闭源），所有"反汇编确认"都是二进制逆向。

## 一、原版的真实架构

不是 7 份独立代码，而是三层：

```
数据层   Wdc*Monitor        （WdcApplicationsMonitor 32 函数、WdcProcessMonitor 26、…）
视图层   Atm*View           （AtmView 13、AtmViewItem 11）
交互层   WdcListView        （31 个函数，其中 26 个是进程专有动作）
```

**推论**：不能按页签切分实现，否则多个模块会同时改 `AtmView::SortDUITree`。

## 二、七页共同遵守的规则（20 条，摘要）

| 规则 | 值 |
|---|---|
| 行高 | UIFILE `TmViewRow` 的 **28rp**（不是代码常量） |
| 子行缩进 | **14rp** |
| 列标题 | **`MUI[colId]` 直接取，不加偏移** |
| 默认排序方向 | 四页首列**都是降序** |
| 字符串排序 | `CompareStringEx(flags = 8 = SORT_STRINGSORT)` |
| 空值 | 数值列用 `1.0` 作哨兵排最后（**这是原版 bug**：真实值 1.0 会被误判为空） |
| 点同列第二次 | 反转方向，只有两态，无"取消排序" |
| 刷新 | 1000 / **500（默认）** / 4000 ms + 暂停 |
| 刷新保持选中 | 用**行 key**，不能用行下标 |
| 分组 | 硬编码 3 组：应用 / 后台进程 / Windows 进程 |

## 三、对我方实现的直接订正

### 3.1 进程分组：原版用子链表，不是 parent-chain

| 项 | 我方 | 原版 |
|---|---|---|
| 建树 | `InheritedFromUniqueProcessId` 爬 8 层 | **每进程自带子链表**（`+0x4A0` 双向链表，内嵌在记录里） |
| 深度 | 限 8 层 | 无限制 |
| pid 复用 | 无校验（已知缺陷） | 靠链表结构规避，**不可能误判** |
| Edge 特判 | 无 | 硬编码 `msedge.exe` / `msedgewebview2.exe` |

原版在进程退出时把整棵子树从聚合器摘掉。**这从根本上绕开了 pid 复用问题。**

### 3.2 用户页的五列数据不在用户页代码里

我方 `RefreshUsers` 自己遍历进程求和 → 会算出**第二套数**，必然和进程页对不上。

原版：`WdcUserMonitor` **完全不写** CPU/内存/磁盘/网络/GPU 的值槽（全镜像扫描 0 条写入指令）。
这些列由**共享聚合器**按 `SessionId` 汇总填充。

正确做法：用户页只负责 (a) 写对列类型掩码；(b) 给行挂上正确 `SessionId`。

### 3.3 详细信息页的 48 列公式不在 `GetColumnText`

`GetColumnText` 不含任何列 ID 比较——它只按**类型标签**把值格式化成文本。
真正的公式在 `WdcProcessMonitor::UpdateProcess`（2850 字节）及其 20 余个填充函数里。

### 3.4 曲线横轴：贴右边缘生长（已修）

原版写入侧 `cursor = 59 - (n mod 60)`，最新样本永远贴右。
开屏时左边一大片是未写入的清零槽位。

### 3.5 「启动影响」不是假功能

数据源：`%WINDIR%\system32\WDI\LogFiles\StartupInfo\<SID>_StartupInfo<N>.xml`（XmlLite 解析）。
阈值：`1000` / `3` / `300` / `0.292`（绝对阈值，磁盘与 CPU 两个维度各自判）。
本机该目录**存在但为空**，所以确实全是「未计量」——这是**缺数据**，不是没实现。

### 3.6 应用历史记录页可以恢复

我方注释里五条「放弃 SRUM」的理由，**四条被证伪**：

- SDK 没公开导出 → 对，但导出表里有（用 `GetProcAddress` 动态取）
- 调 `SruQueryStatsEx` 会 segfault → **调错函数 + 调错签名 + 没 `CoInitializeEx`**，三个错误叠加
- 需要 SYSTEM 权限 → **Administrator + `CoInitializeEx` 即可**，实测拿到 33,954 条记录
- WMI 里没有 SRUM 类 → 对，但原版不走 WMI
- `SRUDB.dat` 被独占 → 对，但原版**不打开这个文件**

接口：`SruQueryStats(type, pStart, pEnd, flags, ppRecordSet)`

**type 的取值以实测为准**（`H04_apphistory.md` §2.3 的表格）：

| type | 实测结果 |
|---|---|
| `0` | `S_OK`，**32,453 条网络记录** |
| `1` | `S_OK`，**108,621 条 CPU 记录** |

> ⚠️ 这份摘要的早期版本把 `0` 写成 CPU、并写了「33,954 条记录」，
> 两处都与实测输出对不上。以本表为准。

## 四、本机无法验证的部分

- **非管理员**能否查询 SRUM（本机只有 Administrator 会话实测）
- 多会话 / RDP 下的用户页行为（本机只有 4 个会话）
- 真实高分屏观感（本机 96 DPI）
- 启动影响的真实数值（本机 WDI 目录为空）
- 组→容器槽的 `+0x10` 偏移差异（需要调试器）

## 五、工具与方法的坑（已记录，避免重犯）

1. **`dumpbin /DISASM` 只覆盖 `.text`** —— 读常量/字符串必须自己做 RVA→raw 换算
2. **`imports.txt` 对「按序号导入」的项顺序不对** —— 会让后续 IAT 槽位全部错位。要用 PE import directory 自己解析
3. **`Class::Method` 名串是 trace 宏的 `(文件, 行号, 方法名)` 三元组**，能定位所属函数但**不是入口**；入口查 `.pdata`
4. **`refs` 找不到 ≠ 没人引用** —— 通过 `.data` 指针表间接访问的搜不到
5. **`va_list` 包装器要读函数体** —— 先存 home slot 再 `lea` 的形态，不看内部会把参数顺序搞反
6. **resstr id 可能被归一化改写** —— 同一个模板有圆括号版/斜杠版
7. **贴命令输出前要原样跑一遍** —— 本轮抓到一个 agent 贴了 `grep -c 'call +qword...'` 输出 9，实际执行输出 0

## 六、`4e0f24b`（横轴修复）的验收依据订正

我在那个提交的说明里写「截图验证：曲线只在最右侧一小段」。**这个验收方法是无效的。**

H10 指出：离屏截图路径（`src/main.cpp:1129`）在存盘前有一个 60 次的循环，
无条件把同一份快照推 60 遍，所以 `hist_.count` **必然饱和到 60**。
而 `n == 60` 正是「与旧公式逐像素相同」的分支 —— **那张图证明不了贴右生长生效**。

代码本身是对的，依据是 H10 的穷举验证：
`span ∈ [1,2999] × i ∈ [0,59]`（179,940 组）确认 `n==60` 时零像素差；
`n==3` 时三个点落 570/580/590（右侧），越界 0 次。

**结论：代码保留，但验收依据要改成穷举验证，不能引用那张截图。**
