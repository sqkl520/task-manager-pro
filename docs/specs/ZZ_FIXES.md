## 零、最终定案：排序会压制分组，但不改用户偏好

### 0.1 原版有三个独立状态字节（我逐条 grep 全部引用点核实）

| 字节 | 位置 | 写入点 | 语义 |
|---|---|---|---|
| `0x35B8` | **视图对象内** | `0x25913`(构造)、`0xA751B`(`SetGroupByType` 内部) | 实际是否分组（组头显隐直接读它） |
| `0x13A721` | 全局 | `0x92FB7` `sete`（在「按类型分组」菜单命令 `0x7705` 的分派里） | **菜单勾选态 = 用户偏好** |
| `0x13C2E8` | 全局 | `0x841FD`(=1)、`0x84223`(=`dl`) | 「分组被排序暂时压制」标记 |

### 0.2 决定性分支（`0x8411C`，反汇编原文）

```asm
1400841E2  test  esi,esi
1400841E4  je    140084209            ; esi == 0 → 「名称列」分支
; ---- 非名称列（CPU/内存/磁盘/网络/GPU）----
1400841E6  cmp   byte[rcx+35B8h],bl    ; 当前是否已分组
1400841EE  cmp   byte[13A721h],bl      ; 用户偏好是否为「分组」
1400841F6  xor   edx,edx
1400841F8  call  1400A7490             ; SetGroupByType(0)  ★ 强制关分组
1400841FD  mov   byte[13C2E8h],1       ; 记下「被排序压制」
; ---- 名称列 ----
140084209  cmp   byte[13C2E8h],bl      ; 之前是否被压制过
140084211  cmp   byte[13A721h],bl      ; 用户偏好是否为「分组」
140084219  mov   dl,1
14008421B  call  1400A7490             ; SetGroupByType(1)  ★ 恢复分组
140084223  mov   byte[13C2E8h],bl      ; 清掉压制标记
```

这就是「列表变平了、但菜单里的勾还打着」的机制：排序只改
`0x35B8`（显示）和 `0x13C2E8`（压制标记），**从不写 `0x13A721`**（用户偏好）。
点回名称列时按 `0x13C2E8` 自动恢复。

### 0.3 我为什么会一度否掉它

第一次排查时我只 grep 了 `0x35B8` 的**直接**写点，看到排序函数
`0x8626C`/`0x85E5C` 不写它，就下了「两者正交」的结论。
但真正的调用在 `0x8411C` 的 `0x841F8`/`0x8421B` —— 它通过
`SetGroupByType` **间接**改 `0x35B8`，所以那次 grep 漏掉了。

教训：`mov [x+off],reg` 这种直接写点全不等于全部写入路径；
封装好的 setter 会把写点藏到别处。

### 0.4 像素侧的独立印证（我自己测）

| 原版截图 | 箭头方向（我扫的像素位置） | 组头 |
|---|---|---|
| `original_win10.png` | 名称列 **▴ 升序** x=112..119 / y=94..97 | **有** |
| `sortname_ours2.png` | 名称列 **▾ 降序** x=113..119 / y=96..99 | **有** |
| `sortname_ours1.png` | CPU 列 x=367..373 | **无** |
| `orig2_full.png` | 内存列 x=439..445 | **无** |

两张名称列图**升降序相反但都有组头** → 分界是「名称列 vs 非名称列」，
不是「升序 vs 降序」。

`sortname_ours1` 的全部 22 个行距我独立测得 27~29.5px

### 0.5 我方实现

`src/tmwindow.cpp`：

```cpp
const bool flatBySort = (sortCol_ != 0);
if (!groupByType_ || flatBySort) { ... 扁平分支 ... }
```

关键：`groupByType_` 只在 `SetGroupByType` 和菜单命令里被写
（我 grep 确认只有 `tmwindow.cpp:309` 和 `tmwindow_menus.cpp:1337`），
排序**从不改它** → 等价于原版「不动 `0x13A721`」。所以不需要引入第三个字节，
结构已经对得上。

验证：`--sortcol=2` 无组头且 3%→2%→1% 严格递减；`--sortcol=0` 有组头按字母序；
`--sortcol=3` 无组头且 4.7GB→1012MB→…→211MB 全局递减。

### 4.2 被推翻的是解析文档自己的可信度声明

| 原声明 | 实测 |
|---|---|
| 「176 个 `@0xNNN` 偏移全部逐字节复核通过」 | 实际 177 个，**10 个对不上**（引用坐标偏 2~4 字节） |
| 「0 处不可解析」 | 与它自己 §0.2 承认的 219 条盲区**自相矛盾** |
| 「token 流是 (属性 id, 值) 扁平交替」 | 严格交替只解释 **48.2%** |
| 「值 = u16 串号且高字节为 0」 | **37.0% 反例** |
| 「`HDR+0x04` = token 流字节数」 | 实际差 15.5 倍，是「节点记录区」的 u16 字数 |
| 节点表字段顺序 `(nodeOff, 名字串号)` | **写反了**，实际是 `(名字串号, nodeOff)` |
| `0x8000 = background` | 错得离谱，`0x8000` 从不取 `window`/`buttonface` |

**这份解析的可信度评级：几何值 A-，格式模型 D。** 结论：**查样式默认值要去节点记录区，不是主 token 流。**

### 4.3 已按审计建议改的注释

## 八、红队核查（ZZ_redteam.md 三条指控的逐条复核）

### 8.1 「组头行高 38 是循环论证」——**不成立**

红队说 `482−173−1=308=28×11` 的算式先假设了中间行高 28。这个批评对**算式**成立，
我已经把那段注释换成直接读填色边界（见 `include/theme.h` 的 `kGroupRowHeight`）。

但红队据此推出「行高既不是 38 也不是 28」是**错的**。我自己逐行扫
`original_win10.png` 的 CPU 列中心 x=390：

```
y=135     #A0A0A0   列头底线
y=136..173          组头热力填色
y=174     #FFF4C4   ← 数据行从这里开始（0% 档）
```

组头 = 136..173 = **38 行**。第二个组头同样：482..519 = 38 行，y=520 起是 `#FFF4C4`。

红队看到的「29 + 9」是**同一个组头内的两段填色**（`#FDF9E5` 29 行 + `#FFF9E4` 9 行），
不是两个不同的行。它把斜切色块误判成了行边界。

### 8.2 「组头值列是 #FFF9E4，一个像素不差」——**成立，但归因错了**

确实不是纯色。CPU 格 `x=357..428` 在 `y=136..157` 是左 50px `#FDF9E5`、
`y=158..164` 变 60px、`y=165` 才全变 `#FFF9E4`。第二个组头是**完全镜像**的
（`y=482..484` 是右 12px `#FDF9E5`，`y=485` 起全 `#FFF9E4`）。

这种严格镜像排除了「随机动画残影」的解释 —— 它更像是原版在 `#FFF9E4` 底上
叠了一层半透明冷色（可能是行首的选中/焦点残留或阴影），只覆盖单元格的一部分。
全图 `#FDF9E5` 出现 1709 次、`#FFF9E4` 出现 9235 次。

我方没有还原这个斜切细节。**记录为已知差异，不改** —— 我没有足够证据确定
它的成因，照抄一个色值只会变成新的假证据。

### 8.3 「排序箭头基线抄错」——**成立，已修**

原版列头带 `y=92..135`（y=135 是 `#A0A0A0` 底线），名称列箭头在 `y=94..97`，
相对列头顶是 **+2**。我旧代码用 `+19`，来源是「列头顶 y=83」—— 那个 83 不是
列头顶。我方旧渲染实测箭头在 `y=64..67`（列头带 45..87），也是 +19。

已改为 `+2`，改后箭头落到 `y=47..50`，与原版口径一致。
