### 2.3 额外发现的头字段（S 未提及）

1. **`0x10 u32 = 0x14`**：节点表的**绝对起始偏移**（不是 `HDR+8`）。
   正确关系是 `节点数 = (HDR - u32(0x10)) / 8`（30001: (0x1a4-0x14)/8 = **50**；30024: (0xac-0x14)/8 = **19**）。
   S 的 `HDR+8` 只有 30001 恰好也能凑出 50 组（因为它在 0x14 起读 50×8 正好读到 0x1a4，
   而 `HDR+8 = 0x1ac` 起读会**越界读到 token 流**）。这是**巧合**，不是正确公式。
2. **duib 实际是三段结构，S 只解析了其中一段**（这是最重要的一条）：

```
0x00  duib / ver=5 / HDR / TBL
0x10  u32 节点表起始偏移 = 0x14
0x14  节点表  (名字串号, 记录偏移) × N         ← 50 / 19 组
HDR   0x1a4 : u32 TOK1 = 0x6bb8              ← 第三段尾部的结束偏移
     0x1a8 : u32 NODEWORDS = 1753            ← 第二段（节点记录区）的 u16 字数
     0x1ac : ── 第二段：节点记录区 ──
              [TOK0, TOK0 + 2*NODEWORDS) = 30001: [0x1ac, 0xf5e)  3506 B / 1753 words
                                          30024: [0xb4,  0x544)  1168 B /  584 words
              ↑ 每条记录 = 一个元素的属性集，按节点表的 记录偏移(偶数, 以 word 计) 切分
              ↑ 验证：50/50（30024 19/19）条记录内部**零个非法 word**，除最后一条外每条
                 起点都精确落在记录边界，且 `最后偏移 + 4 == NODEWORDS`（30001: 1749+4=1753 ✓）
     0xf5e : ── 主 token 流（S 实际分析的就是这一段，共 23642 B）──
              ... 到 0x6bb8
TOK1 0x6bb8: ── 尾部 420 B 的 token 流 ──（118 属性 + 92 值，含 servicestab_* 三个 block）
TBL  0x6d5c: 字符串表描述符
```

3. 节点记录区里放着**全部 24 个样式块（`resid="tab"` / `page` / `drop` / `chart` / …）**，
   以及它们的 `background/font/foreground/padding/borderthickness` 等声明。
   主 token 流（S 的"token 流"）放的是**实例树（元素嵌套）**，尾部 420 B 是**样式覆盖块**。
   `geometry` 出现次数分布：30001 R1=120 / R2=934 / R3=8；30024 R1=57 / R2=155 / R3=0。

4. **`HDR+4` 字段（=1753 / 584）的正确含义**：它是 R1（节点记录区）的 **u16 字数**，
   `R1 结束 = TOK0 + 2 × 该值`，而不是 S 说的「token 流字节数」。
   用 `TOK0 + 该值`（按字节解释）会落在 R1 内部一个非 word 边界上（大量 `x32128` 这类非法 word）——可作为判定依据。

5. 尾部 `[TOK1, TBL)` 的 420 B（30024: 172 B）**不是填充**，是合法 token 数据。S 明确把它排除在外，
   导致 **30001 服 务页的三个样式块（`servicestab_graphs` / `servicestab_tables`）和
   `gpuMemoryChart` 的全部 rp 声明被漏掉**。例如：
   - `servicestab_tables` 里有 `padding = rect(0rp,7rp,0rp,0rp) @0x6d36`、
     `borderthickness = rect(0rp,1rp,0rp,1rp) @0x6d4e`、`bordercolor = threedshadow @0x6d52`
   - 而 S 在 §1.6 写「服务页 `atom(svcList)` **无 rp 声明**（节点只有 `id` + `resstr(33867)`）」——
     **该结论是解析窗口截断造成的假阴性**。

## §2.4 属性 code 映射：几何类全对，`0x8000` 全错

### 几何类（经「同一 code 的全部取值」反证，零反例）

| code | S 的名称 | 实测取值集合（R1 样式区） | 判定 |
|---|---|---|---|
| `0x8015` | borderthickness | 只有 `rect(...)` 3 种 | ✅ |
| `0x8021` | padding | 只有 `rect(...)` | ✅ |
| `0x8023` | margin | 只有 `rect(...)` | ✅ |
| `0x8024` | width | 只有 `1rp / 2rp / 16rp / 60rp / 80rp` | ✅ |
| `0x8025` | height | 只有 `30rp / 32rp / 45rp / 67rp / 80rp` | ✅ |

这 5 个 code **从不出现非几何值**，因此**所有 rp 几何结论的可信度是 A**。

### `0x8000`：S 说是 `background`，实测是「元素续行分隔/元素属性块起始」

S 的原始论据是「`chart` 样式属性 token `@0x27e = 20575`，对应 wdc 的 `background="window"`」。
**实测 `@0x27c` 才是属性 `0x800e`，`@0x27e` 是它的值 `"20575"`。** 而 `0x8000` 在 `@0x280`。
且 `"20575"` 全文件出现 23 次，**前一属性 100% 都是 `0x800e`（23/23），一次 `0x8000` 都没有**。

`0x8000` 的真实取值分布（全 token 流）：

```
"gtf(TEXTSTYLE, 4, 0)" x86   "chartbox" x48   "dtb(CommandModule, 3, 2)" x39
"rect(0rp,0rp,6rp,0rp)" x34  "atom(BarchartModified)" x30   "rect(15rp,0rp,0rp,0rp)" x28
"gtc(TASKMANAGER, 15, 0, 3803)" x13   "middleleft|endellipsis" x7
```

其中 767/1072 次 `0x8000` **后面紧跟另一个属性 id**（即"无值"），只有 305 次带值。
带值时值可以是样式名、字体、颜色、几何、布局串——**不可能是 `background`**。
更符合 DUI 语法的解释是：`0x8000` 是**属性块的分隔符 / `<element>` 的开头标记**
（每开一个新 element 就打一个 `0x8000`），S 在 §0 也自己写过
「`P0` → `P15` ← `0x8000` 的「值」本身又是属性 → 无值布尔」。

>S 把这个 code 判成 `background` 的连带影响：报告里所有"`background=window` / `background=buttonface`"的
>结论都建立在一个**错误归属**上。好在项目代码没有据此改过颜色常量（`U_colors*.tsv` 是直读 uxtheme 的），
>所以**尚未造成实际错误**，但这条必须在 spec 里划掉。

### 另外两个 S 标 ★（"wdc 原文直接证实"）的复核

## §3 token 规则的反例统计

### 3.1 「(attr, value) 扁平交替」的反例

| 指标 | 30001 | 30024 |
|---|---|---|
| word 总数（主 token 流 `[TOK0,TOK1)`） | 13,574 | 3,582 |
| `TOK1 - TOK0` 字节 | 27,148 | 7,164 |
| **能否被 4 整除** | ✓（6787 对） | ✓（1791 对） |
| 按 `(2i=attr, 2i+1=value)` 配对：成立 | 3,321（48.2%） | 815（45.5%） |
| **配对：违反** | **3,571** | **976** |
| attr 后紧跟 attr（值被吃掉） | 3,629 | 706 |
| value 后紧跟 value（裸值/盲区） | 1,610 | 587 |
| **属性 id 落在 0x8000..0x80FF 之外** | **0**（反例 0） | **0** |
| 主 token 流里合法（`< NSTR` 或 `0x80xx`）的 word | **100%** | **100%** |

> 结论：**"每个 word 要么是 0x80xx 属性、要么是合法串号"这一条 100% 成立（0 反例）**。
> 但**"它们严格交替"这一条只有约 47% 成立**。真正的编码是
> \*「属性 id 后面跟 0 个、1 个或 2 个值 word」\*，且当"值"本身是 `0x80xx` 时表示
> \*\*该属性无值\*\*（下一条属性马上开始）。
> 这就是 S 在 §0.1 里隐约察觉到的「0x8010 的现值是一个 0x80xx → 视为带参属性无值」的现象，
> 但他没有把这条规则推广，反而把它当成特例。

### 3.2 「值的高字节为 0」的反例

| | 30001 | 30024 |
|---|---|---|
| 非属性 word 总数 | 5,870 | 1,766 |
| **高字节 ≠ 0** | **2,171（37.0%）** | **404（22.9%）** |
| 出现过的非零高字节 | 0x1 / 0x2 / 0x3 | 0x1 |
| 最大串号 | 838 / 838（= NSTR-1） | 436 / 436 |

**反例示例**（30001 `@0x10f8` 附近）：
`0x1108: 128 "cpu_bheader"` 后面紧跟 `0x110a: 0x8000`——两者之间没有属性 id；
再如 `0x112c: 81 "rect(1rp,0rp,0rp,0rp)"` 紧跟 `0x112e: 206 "Button"`（两个裸值）。
这两处高字节都非 0，说明这**不是 8 位串号 + 8 位属性码**的打包，而是**两个独立 16 位 word**。

### 3.3 S 自己给出的盲区数字复核

| S 的声明 | 实测 | 结论 |
|---|---|---|
| 30001：`219 / 1054` 条几何串前面是值而非属性 | 在 S 的窗口 `[TOK0,TOK1)` 内精确复现：**1054 条几何串 / 3634 个 rp 数字 / 219 条裸值** | **完全吻合**（S 的统计口径诚实） |

> 值得注意：**S 的盲区统计是准的，但他在 §0 结尾写「0 处不可解析」与 §0.1 写「219 条不可判定」自相矛盾**。

> 更可能是**一行里允许「属性 id 后跟 2 个值」**（padding 与 margin 并列），而不是"id 被吃"。

| 类别 | 属性 code |
|---|---|
| **总是带字符串值**（19 个） | 0x8002, 0x8005, 0x800a, 0x800c, 0x800d, 0x800e, 0x800f, 0x8010, 0x8011, 0x8012, 0x8013, 0x8014, 0x8015, 0x8016, 0x8021, 0x8022, 0x8023, 0x8024, 0x8025 |

### 4.3 需要修正的三处「归属/引用」问题（不改数值，但注释与依据要改）

**注 1（重要）：`kHeight=30` 的 "tab style" 在 30001 里其实没被任何元素使用。**
- `"tab"` 在 30001 的 token 流里只被引用 **3 次**：`@0x1ac`（样式名自己的位置）、
  `@0x1b0`（`resid` 的属性）、`@0x1ba`（`resid` 的 值）。
- **`sheet="tab"` 在 30001 中出现 0 次**；`class="WdcTab"` 也是 0 次。
- 30001 里根本没有 tab 控件实例（没有 `atom(tabctrl)` 这个串；30024 才有）。
  30001 是按 4 个 `*tab_graphs` / `*tab_tables` 平铺的页面，页签容器由宿主绘制。
- 30024 里 `sheet="tab"` 只出现 **1 次**（`@0x159e`，元素 `atom(tabctrl)`）。
- ⇒ `kHeight=30` 的**数值仍是原版的**（`30rp` 确实写在 tab 样式里，全局仅此一处），
  但注释「UIFILE tab style 30rp ⇒ 任务管理器页签高 30」缺少"这个样式在 30001 未被实例引用"这一层；
  真实页签高度更可能由宿主（tm 的 C++ 端）或 30024 的 tabctrl 决定。**建议保留 30，但把依据降级。**

**注 2：`kIconLeft` 的语义与 UIFILE 不符（但仍应保留 22）。**
`theme.h:534` 写「`TmFirstColumn.padding.left(6rp) + ExpandoWrapper(22rp) = 图标左沿 28rp`」。
字节层面这两个数字都对，但 6+22=28 **推不出原版的图标左沿**：
`tmwindow_list.cpp:518` 自己已经写过「按 DUI 规则推算箭头应在 x≈14，但实测是 9」。
而 `kRowIconLeft = 30`、`kRowTextLeft = 54`（同文件 134/135 行）与 6+22=28 差 2px。
⇒ **22 这个数值保留，但"6+22=28 就是图标左沿"这条推导应删除**（它已被实测 30 推翻）。

**注 3：`kCellPadTop/Bottom` 的 `rect(4,2,4,3)` 是单元格 padding，不是行高来源。**
代码里 `kCellPadTop=2` / `kCellPadBottom=3` 目前**零引用**（`src/` 里没有使用点），
只有 `kCellPadLeft/Right` 在用。UIFILE 的值是对的，但常量本身是死代码——
这与 memory 里「假功能是本项目最大问题」的模式一致，建议要么落地要么删除。

### 4.4 rp 单位与 DPI

- **`1rp = dpi/96 px` 在本机 96 DPI 下成立，1rp = 1px**（`AppliedDPI=96` 实测）。
- UIFILE 里**量纲不止 rp 一种**，实测清单（30001 / 30024 合计）：
  - `rp`：**431 次**（绝对主力；30001 有 73 个不同字符串含 rp）
  - **`pt`：6 次**，全部是字体尺寸：`"16pt;;;gtf(TASKMANAGER, 17, 0)"`、
    `"12pt;;;Segoe MDL2 Assets"`、`"6pt;;;Segoe MDL2 Assets"`（30001 串 #66/#286/#364）
  - 另有 `size(85rp,23rp)`、`size(23rp,23rp)`、`gradient(...)`、`flowlayout(...)` 等函数式取值
  - **没有** `px` / `dip` / `em` / `in` / `cm` 单位。
- ⇒ 代码注释里「所有几何常量是 96 DPI 基准 px」对**几何**成立；
  但**字体**用的是 `pt`，`16pt @96DPI = 21.33px`，与 rp 不是同一量纲。
  `gtf(TASKMANAGER, 17, 0)` 这类引用是通过主题取字体，`gtf` 前面的 `16pt` 是**回退值**，
  代码里若把它当 rp 用会偏大。目前代码没有直接用这几个串，但**必须记录这条**。

### 5.3 一句话总结

**S 把「概率性成立的启发式」写成了「格式规范」。**
它的**字符串表解析是 A 级、rp 数值是 A 级、属性名映射是 B 级**——所以项目里现有的几何常量全部安全；
但它的 **token 流模型（D 级）和三段区域结构误判（C 级）**意味着：
**任何"UIFILE 里没有这个声明"的否定性结论都不可信**（服务页就是活生生的假阴性），
而 **`HDR+4` 那个字段的定义错误**会让任何想复现解析的人直接走偏。

引用这份 spec 时的正确姿势：**只信它给出的 `@0xNNN → 字符串` 对应关系（167/177 可复核），
不要信它的"token 流结构"和"某属性不存在"这两类结论。**
