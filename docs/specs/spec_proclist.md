## 1. 热力图颜色（最关键，先纠正）

### 1.1 结论一句话

热力图**不是整行着色**，而是**只画在资源列（CPU / 内存 / 磁盘 / 网络 / GPU）的单元格内**。
`名称` `类型` `状态` 三列永远是纯白 `#FFFFFF`【取】。
（现有实现 `src/tmwindow_list.cpp:301-329` 用 `FillSolid(hdc, clip, ...)` 对整行 clip 填色，这一点是错的。）

### 1.2 实测色值（单元格中心、避开文字后取众数）

### 1.4 索引算法

单张低负载截图**无法反解出精确公式**（本图所有值都 <5%，高端完全没有样本）。但可以得到 3 个硬锚点：

| 值 | 颜色 | 对应 part |
|---|---|---|
| `0%`（CPU 列，真 0） | `#FFF4C4` | **part 4**（下标 1）|
| `30.4 MB` = **0.095%** of 31.2 GB | `#F9ECA8` | **part 5**（下标 2）|
| `1,392.4 MB` = **4.36%** of 31.2 GB | `#FFE486` | **part 6**（下标 3）|

> 31.2 GB 来自同机 perf 页（`images\3.png`：`6.5/31.2 GB (21%)`）。

**关键推论：分母是"总量"，不是"列内最大值"。**
内存列里 `67.3 MB`（列表最大）与 `30.4 MB`（列表约 1/2）**实测同色**（`#FBEAA9` vs `#F9ECA8`，JPEG 噪声内同色）。
如果按列内最大值归一化，两者应差一整档。所以：
分母 = **物理内存总量（31.2 GB）**，CPU/磁盘/网络 = **100%**。
→ 现有 `src/tmwindow_list.cpp` 的 `val / maxMem_`（按列内最大值归一化）**必须改掉**。

三条锚点同时成立 ⇒ **单调递增、低端极陡**：`part 3` 在实践中不出现，`0.1%` 就吃掉一档、`4.4%` 又吃一档。
这排除了线性映射（线性的话 0.095% 和 4.36% 会落在同一档），也排除了"按列内最大值归一化"
（那样 CPU 0% 会落到最浅档 `part 3`，实际是 `part 4`）。

可用实现（`pct` = 占该列**量程**的百分比：CPU/磁盘/网络 量程 100%，内存量程 = 物理内存总量）：

```cpp
// = TaskManager part 3..12（注意最后两项同色，色阶实际只有 9 种）
static const COLORREF kHeatFill[10] = {
    RGB(0xFF,0xF9,0xE4), RGB(0xFF,0xF4,0xC4), RGB(0xF9,0xEC,0xA8), RGB(0xFF,0xE4,0x87),
    RGB(0xFF,0xD2,0x64), RGB(0xFF,0xC6,0x3D), RGB(0xFC,0xB8,0x16), RGB(0xFC,0xA7,0x1D),
    RGB(0xFC,0x68,0x2A), RGB(0xFC,0x68,0x2A),
};
// 上界（含）。[0]=-1 是哨兵：让下标 0 永远选不到，于是 0% 落到 part 4。
// 前 4 个上界由截图锚点唯一确定；后 6 个按对数趋势外推【推】
static const double kHeatUpper[10] = { -1.0, 0.05, 1.0, 5.0, 12.0, 24.0, 40.0, 58.0, 76.0, 1e9 };

inline COLORREF HeatColor(double pct) {
    if (pct < 0) pct = 0;
    for (int i = 0; i < 10; ++i) if (pct <= kHeatUpper[i]) return kHeatFill[i];
    return kHeatFill[9];
}
// 自检（必须全部通过）：
//   HeatColor(0.00)  == 0xFFF4C4   // 4.png CPU 0% 行
//   HeatColor(0.095) == 0xF9ECA8   // 4.png 内存 30.4 MB 行
//   HeatColor(4.36)  == 0xFFE487   // 6.png 内存 1,392.4 MB 行
```

【推】`kHeatUpper[4..9]` 是外推的，需要一张 ≥50% 负载的截图做回归才能定死。
若不想猜，可先只用实测确定的前 3 档（`0 → part4`、`(0,1] → part5`、`(1,5] → part6`），
高端暂时线性接到 `#FC682A`，等有截图再校。

⚠ 关于"CPU 列 2% 那一行"：截图里 CPU **列头**显示汇总 `2%`，但**列表内 CPU 列的单元格全部被右键菜单遮住**
（x=517..586 落在菜单 x=440..618 之下），只有第 14–18 行的 `0%` 可见。
因此**无法从本图取到"CPU 2% 行"的单元格颜色**。

注意：`part 11` 与 `part 12` 的 fill 完全相同（都是 `#FC682A`），
说明**色阶实际只有 9 种颜色**，数组第 10 项不是笔误，是主题里就是这么写的。

### 1.5 文字颜色

* 热力格内的数字：**`#000000`**（ClearType 核心像素 `#1C131D…#3A2940`）【取】
* 不需要"高值反白"——即使 100% 用 `#FC682A` 也是深色黑字（扫描中所有热力格文字都是黑字）【取】+【推】

### 1.6 单元格填充几何

* 填充**铺满整个单元格**：横向从列左边界到列右边界，纵向整行高 28px
* **无内缩、无圆角、无边框**【取】
* 列分隔线（x=587/588、x=660）画在填充**之上**（分隔线像素是 `F0DFA7` / `F8ECA8`，是分隔线与黄色混合）【取】

## 5. 分组结构

* 分组头 = `chevron` + `图标` + `名称 (n)`。
* `(n)` = 该应用下的进程总数（`迅雷 (13)` 表示 13 个进程）。【取】+【推】
* **只有 `类型 == 应用` 的分组才带 `(n)` 且加粗**。
  反例（都实测过）：
  * `火绒安全软件 安全服务模块`（后台进程）有 chevron、无 `(n)`、不加粗【取】
  * `Tailscale service` 第 12 行（后台进程）有 chevron、无 `(n)`、不加粗；与第 9 行同名字无 chevron 的条目**墨迹完全一致**（都是 89px 宽）【取】
  * `桌面窗口管理器`（Windows 进程）无 chevron、无 `(n)`、不加粗【取】
* 有子进程的就画 chevron（`>` 折叠 / `⌄` 展开），与本行是否应用无关。【取】+【推】
* 分组头背景无差异（白 `#FFFFFF`）。【取】
* 缩进：截图中所有条目都是顶层（chevron 恒在 x=19、图标恒在 x=40），**量不到子项缩进**。
  建议子项 **+20px**，且子项不画 chevron。【推】

### 必须改的五处（相对现状）

1. `HeatColor()` 的 11 项数组要砍成 10 项，删掉自造的 `#F05A14`；索引按上表。
2. **归一化分母改为量程**：内存用 `物理内存总量`，CPU/磁盘/网络用 100。
   现在的 `val / maxMem_`（列内最大值）是错的 —— 截图里 67.3 MB 和 30.4 MB 同色就是反证。
   同理删掉 `heatT = std::sqrt(raw)` 的开方压缩，色阶本身已经是陡峭的低端曲线。
3. 热力图**只填资源列单元格**，不填整行（`名称/类型/状态` 恒白）。
4. 行高 `32 → 28`。
5. `类型` 列补上（`应用/后台进程/Windows 进程`，直接复用 `classifier.cpp` 的 `ProcessGroup`）。
