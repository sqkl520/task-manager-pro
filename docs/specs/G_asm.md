# 问题 1：热力图（heat map）调色板与归一化

## 1.1 结论摘要（已证实）

**原版热力图不是"按列最大值归一"，也不是"按物理总量归一"，更没有任何 pow/log 压缩。
它用的是「设备主题里的一张 9 档固定色表 + 一组固定的百分比阈值 9/19/39/59/79/99」。**

调色板**不是硬编码的**，而是运行时用 `OpenThemeData(NULL, L"TASKMANAGER")` 打开
主题后，用 `GetThemeColor()` 逐条读出来的；程序里只有一张"颜色放哪儿 / 第几档"
的**描述表**。真正写进程序的是**阈值的 double 值**（9/19/39/59/79/99）。

### (c) 真正的着色（分桶）函数 —— **RVA `0x74B04`，共 0xB0 字节**

这是全程序**唯一**把数值变成颜色的地方（调用点共 7 处，全部是行绘制代码）。
函数签名从调用点反推为：`COLORREF f(double percent /*xmm0*/, char highlighted /*dl*/)`。


**这条函数证明了**：
- **没有 pow / log / sqrt / 分段线性压缩**。全程序只 import 了 `ceilf`、`floorf`、`sqrtf`
  三个浮点数学函数（`api-ms-win-crt-math-l1-1-0`），且都没有出现在此路径上（见 1.5 节）。
- **输入必须已经是 0–100 的百分比**，因为阈值就是 9/19/39/59/79/99/100。
- 数字到颜色的映射是**纯阶梯查表**（step function），不是渐变插值 —— 所以界面
  上会出现"同色相邻行跳变"，这也解释了为什么实测只有少数几个离散色值。
- `255.0` 是"无数据/不适用"哨兵，直接涂最浅的 `#FFF9E4`。

### (e) 归一化分母 —— 部分解决

- 分桶函数**只接受已算好的百分比**，它自己不做任何除法。所以分母在**上游**。
- 上游结构：行绘制函数里 `rsi = [monitor+0x50] + colIdx*24`（`0x982A1`–`0x982AD`），
  即**每列一条 24 字节记录**，颜色值/百分比存在 `[rec+8]`：
  - 走 `0x74B04` 时把 `[rec+8]` 当 **double 百分比**读（`0x98533: movsd xmm0,[rsi+8]`）
  - 走快捷路径时把 `[rec+8]` 的低 32 位当 **已算好的调色板下标 int** 读
    （`0x552AD: mov ecx,dword ptr [r12+8]`），然后同样用 `idx*24` 查表
  → 说明这是个 union：`{ float pct; int colorIdx; }` 或者 `{ float pct; int pad; }`
    外加上层已缓存索引。
- **能确定的**：分母是**每列各自算的**，CPU 列得到的是"占全部处理器"的百分比
  （有 `AllProcessCpuUsage: %f` 这个格式串，RVA `0x10AE78`）。
- **不能确定的**：内存/磁盘/网络/GPU 列各自的确切分母表达式。需要继续追
  `[monitor+0x50]` 数组的填充点，本轮未完成（见 1.6）。

### (f) 有没有 pow/log —— 已证实没有

`.rdata` 里未被引用的宽字符串包含大量调试格式串，但**导入表里浮点数学只有 3 个**：

```
api-ms-win-crt-math-l1-1-0.dll
     7D ceilf
    117 sqrtf
     BF floorf
```

全程序 `mulsd` 157 处、`divsd/divss` 若干，但没有一处 `log`/`pow` 的调用点。
`sqrtf` 的 3 个调用点都在 GPU/图表缩放，不在热力路径上。
**结论：热力图没有做任何对数/幂次压缩，纯粹是"线性百分比 → 阶梯查表"。**

# 问题 2：数值格式化

## 2.0 总架构（已证实）—— 格式串全部在 MUI 里，不在 exe 里

原版**没有把任何 `"%.1f%%"` 之类的格式串硬编码进 exe**。它用的是：

```
TmFormatMessageBuffer(strId, ...)   ← RVA 0x69F4，带 hash 表的 STRINGTABLE 缓存
        ↓
LoadStringW(g_hInst, strId, buf, 0x400)   ← 直接读 MUI（zh-CN/Taskmgr.exe.mui）
        ↓
TmPrintOrFormatBuffer(...)  ← RVA 0x66584，负责 %.1f / %.2f / %s%% 等
```

来源：`0x1F4E8` 处 `LoadHeatmapColorsFromTheme` 的兄弟函数；以及 `0x69F4` 里的
`call 0x6B90` → `LoadStringW`（IAT `0x1400EE320`）。这是原版取字符串的**唯一**路径。

因此，问题 2 的答案必须从 **MUI 的 STRINGTABLE** 里找，而 exe 里只有 **strId 常量**。
我把 MUI 用严格 RT_STRING 解析器（`docs/evidence/exec/g/mui2.js`）完整解出来了（982 条）。

## 2.1 MUI 字符串 ID 的正确偏移规则（已证实，重要的方法论订正）

我一开始按 `strId = colId + 1` 去查 MUI，**48 列里只命中 35 列，13 列取到空串**。
【2026-11-24 订正：本条错误】正确规则是 **`strId = colId`**，基址 32003。实测 20/20 逐条命中（名称/PID/用户名/…）。原文的 `+16` 是把 "MUI STRINGTABLE 块起始" 与 "列 id 起始" 搞混了。详见 docs/audit/H00_plan.md §0.1 第 6 条。

原因：exe 里的 `colId` 和 MUI 的 `strId` **不在同一个编号空间**：
- exe 的 colId 从 32003 起（0x7D03），是**列 ID**
- MUI 的 STRINGTABLE 块 2001 覆盖 32016–32031（0x7D10–0x7D2F）
- 两者差 **16**，而列池里 48 条记录是**乱序**排列的，所以必须用 +16 才能对齐

**48/48 命中的列名与 MUI 块 2313（详细信息页列名表）语义完全一致**，这是硬证据。

## 2.1b 进程页数值格式化模板（已证实，同 +16 规则）

MUI 块 2315 的 16 条原文（逐条，无分隔）：

```
[ 0] ""
[ 1] "%s MB"
[ 2] ""
[ 3] "%s 毫秒"
[ 4] ""  [ 5] ""  [ 6] ""  [ 7] ""
[ 8] "%s MB"
[ 9] "%s MB/秒"
[10] "%s Mbps"
[11] "%s%%"
[12..15] ""
```

块 2315 基址 = 2315 × 16 = **37040**（0x90B0）。所以在 MUI 文件里：
`0x90B1 = "%s MB"`、`0x90B3 = "%s 毫秒"`、`0x90B8 = "%s MB"`、
`0x90B9 = "%s MB/秒"`、`0x90BA = "%s Mbps"`、`0x90BB = "%s%%"`。

代码里 `WdcDataMonitor::GetColumnText`（RVA 0x6688A）用 **`0x90A1` `0x90A3` `0x90A8` `0x90A9` `0x90AA` `0x90AB`** 这 6 个常量，正好等于上述 6 个模板 **减 0x10**。
── 与 2.1 的 `colId + 16` 是**同一个偏移**，互相印证。

## 2.2 CPU 百分比格式（已证实 + 一处修正）

原实现假设的三段式：
- `<0.05` → `0%`
- `<1` → `%.1f%%`
- 否则 `%.0f%%`

**逐项核实结果：**

| 假设 | 结论 | 证据 |
|---|---|---|
| `%.0f%%` | ✅ **证实** | MUI `0x8660` = `"(%.0f%%)"`（带括号，用于「性能页」侧栏）；进程页用 `%s%%`（`0x90BB`），数字部分另用 `%1.0f`/`%.0f` |
| `%.1f%%` | ⚠️ **部分证实** | `.rdata` 宽串 `0x1061E0` = `"%.1f"`，被 `0x73DAE` 与 `0x756D5`（`TmPrintOrFormatBuffer`）引用 |
| `<0.05 → "0%"` | ✅ **证实**（但语义不同） | 见下 |

### `<0.05` 分支的真相

常量 **`0x110E88 = 0.05`**（double），只在 3 处被读：
`0x6FCA0`、`0xCA4F0`、`0xCF94C`。其中 `0xCA4F0` 处的用法是：

```asm
1400CA4E1  movsd  xmm1,[rbp+40h]              ; xmm1 = 百分比值
1400CA4E6  comisd xmm1,[140110EC0h]           ; 0x110EC0 = 99.95
1400CA4EE  jae    1400CA507                   ; >= 99.95 → 走 A
1400CA4F0  movsd  xmm0,[140110E88h]           ; 0.05
1400CA4F8  comisd xmm0,xmm1
1400CA4FC  ja     1400CA507                   ; 0.05 > v → 走 A
1400CA4FE  mov    dword [14013C2C0h],r14d     ; 落在 [0.05, 99.95) → 标志=1
1400CA505  jmp    1400CA50E
1400CA507  and    dword [14013C2C0h],0        ; 否则 → 标志=0
```

即：`flag = (0.05 <= v < 99.95)`。

**这不是"小于 0.05 显示 0%"，而是一个"是否需要特殊处理"的布尔开关**（推测用于
"是否显示 0%/-/-/100%" 的判定）。真正的 `0%` 字符串在 MUI 里：

| strId | 内容 |
|---|---|
| `0x8430` | `"0"` |
| `0x8431` | `"0%"` |
| `0x8432` | `"0%"` |
| `0x8433` | `"0%"` |
| `0x8434` | `"0%"` |
| `0x843C` | `"100%"` |
| `0x843D` | `"已暂停"` |
| `0x843E` | `"4 分钟"` |
| `0x843F` | `"60 秒"` |
| `0x8440` | `"30 秒"` |

**四个重复的 `"0%"`** 强烈暗示这是**四个仪表盘/图例**的占位串，不是 CPU 列。
CPU 列本身的 `0%` 由 `%s%%` + 数字 `0` 拼出来（即 `"0"` + `"%"`）。

**结论**：我们实现的 `<0.05 → 0%` 在**效果上正确**（原版确实会把极小的值显示成 `0%`），
但**机制不同**：原版是 `fabs(v) < 0.05 → 用整数字符串 "0"`，不是直接返回字面量 `"0%"`。
**没有 `%.1f%%` 这一档的证据** —— 原版进程页 CPU 列是 `%.0f` 取整后加 `%`。
`%.1f` 只在「性能页」的 60 秒/4 分钟利用率图上用到。

## 2.3 内存列：千分位（已证实）与 MB→GB 阈值（已证实）

### (a) 千分位 —— 真实存在，且是 Win32 区域感知的

`GetNumberFormatW` 被导入（IAT `0x1400EDA80`）且有 **12 个真实调用点**。
`WdcDataMonitor::GetColumnText`（RVA `0x6688A`）内部：

```asm
140066B0B  mov  ecx,400h                  ; cchOut
140066B10  mov  [rsp+20h],rdi             ; lpNumberStr（刚格式化的 "1392.4"）
140066B15  call qword ptr [1400EDA80h]    ; ★ GetNumberFormatW → 加千分位
140066B1C  test eax,eax
140066B23  jg   140066B44                 ; 成功 → 用加了分隔符的串
```

**结论**：
- 千分位**确实存在**
- 分隔符**跟随系统区域设置**（中文 Windows = `,` → `1,392.4`）
- 小数位数由 `lpFormat` 的 `NUMBERFMT` 决定，不是硬编码

### (b) MB → GB 阈值 = **1024 MB**（已证实）

RVA `0xBA0D4` 是**字节数的自动单位换算器**（`AtmBaseView::GetBestFitUnit` 的底层）。
三条阈值判断（`rax` = 字节数）：

```asm
1400BA13C  cmp  rax,400h           ; 1024
1400BA142  jae  1400BA157
   → < 1024 字节：strId 0x865B，不除
1400BA157  mulsd xmm1,xmm5         ; xmm5 = 0x110E80 = 0.0009765625 = 1/1024
1400BA18C  cmp  rax,400h
1400BA198  cmp  rax,100000h        ; 1 MiB
1400BA19E  jb   1400BA1F8
1400BA1A0  cmp  rax,40000000h      ; 1 GiB  ★
1400BA1AB  jb   1400BA1CB
1400BA1AD  mulsd xmm1,[140110E78h] ; 9.313225746e-10 = 1/2^30  → GB
1400BA1C1  mov eax,865Ah           ; GB 模板
1400BA1CB  mulsd xmm1,[1400F4DD0h] ; 9.536743164e-7  = 1/2^20  → MB
1400BA1DF  mov eax,865Dh           ; MB 模板
1400BA1F8  mulsd xmm1,xmm5         ; 1/1024 → KB
1400BA20D  mov eax,865Ch           ; KB 模板
```

**换算表（已证实，全部是 2 的幂）**：

| 字节范围 | 单位 | 除数 | 倍数（double） |
|---|---|---|---|
| `< 1024` | 字节 | 1 | — |
| `< 1048576` (1 MiB) | **KB** | 2^10 | `0.0009765625` = `0x110E80` |
| `< 1073741824` (1 GiB) | **MB** | 2^20 | `9.5367431640625e-7` = `0xF4DD0` |
| `>= 1073741824` | **GB** | 2^30 | `9.313225746154785e-10` = `0x110E78` |

> **MB→GB 的切换点是 1 GiB = 1073741824 字节 = 1024 MiB。**
> 不是 1000 MB，也不是 2048 MB。**是 1024 MB**。这是唯一权威答案。

### (c) 内存列保留几位小数（已证实有 1 位和 0 位两套）

MUI 块 **2148**（0x8640）第 10–13 条：

| strId | 内容 |
|---|---|
| `0x864A` | **`%0.1f MB %s`** ← 1 位小数 |
| `0x864B` | **`%0.1f GB %s`** ← 1 位小数 |
| `0x864C` | **`%1.0f MB %s`** ← 0 位小数 |
| `0x864D` | **`%1.0f GB %s`** ← 0 位小数 |

同块还有 `0x864E = "%u MHz"`、`0x864F = "%s KB"`。

`0xBA1E7` / `0xBA24E` 的 `cmp r10d,2 / cmovne eax,[rax-4]` 就是在这
**1 位小数版和 0 位小数版之间切**（`r10d` 是调用方传入的"精度样式"）。
同一个 `%s` 位置再被套上千分位后的数字串。

> 所以 `1,392.4 MB` 这个实测值完全对得上：`%0.1f` → `1392.4`，
> 再经 `GetNumberFormatW` → `1,392.4`，再套 `%s MB` → `1,392.4 MB`。**全链闭合。**

# 问题 3：排序比较器

## 3.1 架构（已证实）：统一分派，不是每列一个比较器

原版**没有给每列写独立比较器**。它有一个**按列类型掩码分派**的通用比较器，
通过 DUI 的 `Element::SortChildren(compareFn)`（IAT `0x1400ED5F0`，10 个调用点）挂上去。

关键调用点：

| 调用点 | comparator | 用途 |
|---|---|---|
| `0x7E9FF` | `0x7E510` | `WdcDataMonitor::Sort`（单列） |
| `0x7EA7D` | **`0x7F880`** | 分组内排序 |
| `0x7EAA4` | **`0x7F880`** | 整表排序 |

## 3.2 名称列：`CompareStringEx`，**dwCmpFlags = 0x18（不是 8）**

```asm
140005BEC  mov  r11,rsp
140005BF3  xor  eax,eax
140005BF5  or   r9d,0FFFFFFFFh      ; cchCount1 = -1
140005BFD  mov  r8,rcx              ; lpString1
140005C00  mov  [r11-20h],rax       ; lpReserved = NULL
140005C04  xor  ecx,ecx             ; lpLocaleName = NULL（当前用户区域）
140005C0A  mov  [r11-30h],r9d       ; cchCount2 = -1
140005C0E  mov  [r11-38h],rdx       ; lpString2
140005C12  lea  edx,[rax+18h]       ; ★ dwCmpFlags = 0x18
140005C15  call qword ptr [1400EE608h]   ; CompareStringEx
140005C21  cmp  eax,2               ; CSTR_EQUAL
140005C24  sete al                  ; return (== CSTR_EQUAL)
140005C2B  ret
```

**`dwCmpFlags = 0x18`**：

| 常量 | 值 | 说明 |
|---|---|---|
| `SORT_DIGITSASNUMBERS` | `0x00000008` | 数字按数值排（"文件2" < "文件10"） |
| `SORT_STRINGSORT` | `0x00000010` | **额外置位**：标点参与排序，不忽略 |

`0x08 | 0x10 = 0x18`。

> ⚠️ **订正既有结论**：`_CONTEXT`/`_SUMMARY` 记的是 `CompareStringEx(NULL, 8, ...)`，
> 实际是 **`0x18`**。`SORT_STRINGSORT` 会让 `"a-b"` 与 `"ab"` 的次序不同。

**注意**：`sete al` 说明它返回的是 **bool（是否相等）**，被两个调用点
（`0x7078`、`0x5B1E6`）用 `test al,al / jne` 消费 —— 这是**分组边界判等器**，
不是全排序的三路比较器。

## 3.3 数值列比较器：`0x7F880` → `0x80950`（已证实）

`0x7F880` 是簿记跳板：

```asm
14007F880  mov  r9,[rdx]                ; 记录B
14007F883  mov  r8,[rcx]                ; 记录A
14007F886  mov  edx,[14013C2A8h]        ; 全局：排序方向
14007F88C  mov  ecx,[14013C2A4h]        ; 全局：排序列 colId
14007F892  jmp  140080950
```

真比较器 `0x80950`：

```asm
140080988  mov  rcx,[r14+50h]           ; 列记录数组
14008098F  lea  rbx,[rax+rax*2]
140080993  mov  r9d,[rcx+rbx*8]         ; 列类型掩码
14008099A  and  eax,7C000000h           ; 取高 6 位类型
14008099F  cmp  eax,10000000h           ; → 字符串
1400809AA  cmp  eax,20000000h           ; → double（0 特判）
1400809B5  cmp  eax,24000000h           ; → double
1400809C0  cmp  eax,28000000h           ; → int64
1400809C7  cmp  eax,40000000h           ; → double（1.0 特判）
```

| 类型掩码 | 比较 | 反汇编位置 |
|---|---|---|
| `0x10000000` | 字符串：`CompareStringEx`（`0x80B38`），相等再按 `cvttsd2si [+8]` 比数值 | `0x80AEC`–`0x80B93` |
| `0x20000000` | double，`and r9d,3FE0000h; cmp 100000h` 特判子类型 | `0x80A7A`–`0x80AE7` |
| `0x24000000` | double，`comisd` | `0x80A62` |
| `0x28000000` | **有符号 int64**，`cmp qword / jl / jle` | `0x80A06` |
| `0x40000000` | double，对 `1.0` 特判 | `0x809CE`–`0x80A01` |

**比较的是原始 double / int64，不是格式化后的文本** —— 证据：

```asm
140080A8E  movsd  xmm0,[rcx+rbx*8+10h]   ; A 的列值（double）
140080A94  movsd  xmm1,[rax+rbx*8+10h]   ; B 的列值
140080A9A  comisd xmm1,xmm0
140080A0A  mov    rdx,[rax+rbx*8+10h]    ; int64 路径
140080A0F  cmp    [rcx+rbx*8+10h],rdx
```

值位于列记录 **`+16`（0x10）** 的 8 字节槽，即 `[列数组 + idx*24 + 16]`。

## 3.4 排序方向（已证实二态，**未证实"第三次点击复位"**）

全局状态：

```
RVA 0x13C2A4  dw sortColumnId    (写: 0x5B596, 0x9E74C)
RVA 0x13C2A8  dw sortDirection   (写: 0x5B59C, 0x9E755)
```

`0x7155` 拿 `0x13C2A8` 与 `-1` 比 → **初值 / 未排序时是 `-1`**。

方向在比较器末尾统一应用：

```asm
140080BA1  imul edi,r12d     ; r12d = direction
140080BA5  neg  edi
140080BA7  mov  eax,edi
```

点击处理（`0x85C6E`–`0x85C89`）：

```asm
140085C6E  mov  eax,[rsi+18Ch]     ; 当前方向
140085C77  mov  edx,[rsi+188h]     ; 当前列
140085C7D  neg  eax                ; 非0 → CF=1，0 → CF=0
140085C7F  sbb  r8d,r8d            ; 0 或 -1
140085C86  dec  r8d                ; -1 或 -2
140085C89  call 14008626C          ; ChangeSortFlag(this, colId, dir)
```

`ChangeSortFlag`（`0x8626C`）的短路条件：

```asm
140086293  cmp  [rcx+17Ch],edx     ; 列变了？
140086299  jne  1400862A8
14008629B  cmp  [rcx+180h],r8d     ; 方向变了？
1400862A2  je   140086465          ; 都没变 → 直接返回
```

**只有"同列 + 同方向"才短路**，没有任何"第三次点击 → 清空排序列"的分支。

> **结论**：
> - **只有升序 ↔ 降序二态翻转**，没有"第三次点击恢复默认排序"（高概率，未 100% 排除
>   上层还有一层三态包装）。
> - 数值列**默认降序**（CPU/内存/磁盘/网络/GPU 都从大到小）。

## 3.5 排序稳定性 —— **未解决**

## 5.1 位掩码地址订正（已证实）

**`_SUMMARY.md` 写的 `0x0F3ED0` 不是错值，而是「文件偏移」，被误当成了 RVA。真实 RVA 是 `0xF5AD0`。**

搜索方法：全文件搜 dword `9D 20 00 00`，全镜像**唯一命中**在文件偏移 `0xF3ED0`，
对应 **RVA `0xF5AD0`**。差值是 **0x1C00 = 7168**，正好等于
`.rdata` 段的 `vaddr - rawptr`（`0xE6000 - 0xE4400 = 0x1C00`）。
也就是说旧报告把 **`.rdata` 的文件偏移**当成了 RVA。


二进制 `0000 0000 0000 0000 0010 0000 1001 1101`，置位 = **0, 2, 3, 4, 7, 13**。

## 本轮的教训（供后续 agent 参考）

1. **不要用宽松模式扫 MUI 字符串**。RT_STRING 的块内长度前缀必须严格按
   `[u16 len][len 个 u16]` 解析。我第一版用"遇到 `00 00` 就切"的启发式，
   结果整个 2313/2314/2315 块的编号**偏了 6**，差点写出错误的列名映射。
2. **exe 里的 strId 与 MUI 的 strId 差 16**。验证方法：拿一个已知正确的
   子集（服务页 5 列 / 详细信息页 7 列）跑命中率，`+16` 是 48/48，`+1` 只有 35/48。
3. **`0x0F3ED0` 是 `.rdata` 的文件偏移不是 RVA**。`.rdata` 的 `vaddr=0xE6000`、`rawptr=0xE4400`，
   差值 0x1C00。**每个段各有自己的差值，不能套用同一常量。**
4. **临时追加内容用延后写入**。我用 shell heredoc 追加时，反引号被 shell 吃掉
   导致反引号内容丢失；中途多次截断重写还意外丢掉了 Q3/Q4。**应先写独立
   `.md` 片段文件再用 Node 拼接**。
