# 08 — 详细信息页 锐评（`src/tmwindow_details.cpp`）

状态：**已完成**（本轮审查）
审查对象：`kDetCols` / `PaintDetailsPage` / `RebuildDetailRows` / `SyncDetailSelection`

---

## 0. 头条结论

**`kDetCols` 的列族选错了。** 本项目把「详细信息页」当成 STRINGTABLE 2313 的 7 个列名
去实现，但 2313 是**进程页列族（37xxx）**的名字表；详细信息页真正的列族是
**32xxx（STRINGTABLE 2001–2004，共 48 列）**。据此可确定：

- 原版详细信息页**默认只有 6 列**：`名称 | PID | 状态 | 用户名 | CPU | 内存(活动的专用工作集)`
- 原版详细信息页**没有「类型」列**（32xxx 列族里根本不存在「类型」这个词）
- 原版另有 42 列在「选择列」里可选（I/O 字节、页面错误、路径名称、描述、平台、特权…）

重实现是 9 列，且顺序/列名/列宽/默认可见集合全部与原版不同 —— **6 列里 4 列不对，
另外多出 3 列不该默认显示**。

## 1. 关键调研：完整默认列清单到底是哪一组

### 1.1 先纠正一个 ID 算术关系（这是全部结论的基础）

列 ID 与它的名字字符串 ID 是 `colId = strId - 1`。验证：

| 列族 | 列 ID | 名字字符串 ID | 来源表 |
|---|---|---|---|
| 进程/应用页 | 37001…37007 | 37002…37008 | **STRINGTABLE 2313** |
| 进程/应用页续 | 37008…37023 | 37009…37024 | **STRINGTABLE 2314** |
| 详细信息页 | 32001…32055 | 32002…32056 | **STRINGTABLE 2001–2004** |

`node _probe/tm/rsrc.js` 重解析确认（我另写脚本按 slot 序号展开，见下）：

```
=== BLOCK 2313 baseId=36992
  slot10 id=37002 "名称"   slot11 id=37003 "PID"    slot12 id=37004 "类型"
  slot13 id=37005 "状态"   slot14 id=37006 "发布者" slot15 id=37007 "进程名称"
  slot16 id=37008 "命令行"
=== BLOCK 2001 baseId=32000
  slot4 id=32004 "名称"  slot5 id=32005 "PID"  slot6 id=32006 "用户名"
  slot7 id=32007 "会话 ID" slot8 id=32008 "CPU" slot9 id=32009 "CPU 时间"
  ... 直到 slot16 id=32016 "内存(共享工作集)"
=== BLOCK 2002 → 32017…32032（提交大小…I/O 其他字节）
=== BLOCK 2003 → 32033…32048（路径名称…组）
=== BLOCK 2004 → 32049…32056（逻辑磁盘…硬件强制堆栈实施的保护）
```

**所以 2313 的 7 个名字 = 列 37001–37007 的名字**，即
`名称 / PID / 类型 / 状态 / 发布者 / 进程名称 / 命令行`。

### 1.3 默认「可见」是哪几列：`.rdata` 里的可见性位掩码

详细信息页的状态记录是一个**结构清晰的三段式**：`掩码 → 一个 32 → 48 个宽度`。
**同一份记录在 exe 出厂默认值和注册表当前值里各出现一次，逐字节相同** —— 这是决定性证据。

**exe 出厂默认（`0x0F3ED0`）**
```
0x0F3ED0: 0000209D      ← 可见性位掩码 = 8349
0x0F3ED4: 00000020      ← 32（疑似列数上限/版本，两处都是 32）
0x0F3ED8: 48 个宽度，依次对应池索引 0..47
0x0F3F98: 0,1,2,3,…,47  ← 与宽度表一一对应的索引数组
```

**注册表当前值（`_probe/tm/reg_Preferences.bin` @ `0x0FB8`）**
```
0x0FB8: 0000209D      ← 同一掩码
0x0FBC: 00000020      ← 同一 32
0x0FC0: 100,100,50,80,80,50,50,40,80,60,… （48 个，与 exe 那份完全相同）
```

**两处逐字节一致 ⇒ 该用户从未改过详细信息页的列，屏上跑的就是出厂默认。**

`0x209D = 8192 + 157 = 8349`，二进制位 = **{0, 2, 3, 4, 7, 13}**。
按池索引映射（池 = `0x0F4328` 起 48 条的槽位顺序，§1.2-B）：

| bit | 池索引 | 列 | 记录里的宽度 |
|---|---|---|---|
| 0 | 0 | **名称** | 100 |
| 2 | 2 | **PID** | 50 |
| 3 | 3 | **状态** | 80 |
| 4 | 4 | **用户名** | 80 |
| 7 | 7 | **CPU** | 40 |
| 13 | 13 | **内存(活动的专用工作集)** | 80 |

**验证这个映射不是巧合（三步排除）：**

1. **若按「MUI 字符串表出现顺序」解释这 6 个位**（名称/PID/用户名/会话 ID/CPU/
   CPU 时间/周期/…）：会选出 `名称 + 用户名 + 会话 ID + CPU + CPU 时间 + 内存(共享工作集)`
   —— **少了状态、少了内存(活动专用)，多了两个不该默认显示的列**。不成立。
2. **若按「池内可见项顺序」**（跳过描述这种宽度 0 的）：会选出
   `名称 + PID + 用户名 + 会话 ID + CPU + 内存(活动专用)` —— **同样少了状态**。不成立。
   （因为池里 `状态` 在 idx 3、`用户名` 在 idx 4，中间没有可跳过的项，位 3/4 必须
   连续置位才能两个都要 —— 而 0x209D 的 bit3、bit4 **确实连续置位**。）
3. **只有「直接按池槽位」读**才落出
   `名称 | PID | 状态 | 用户名 | CPU | 内存(活动的专用工作集)` —— 经典六列。
   ⇒ **池槽位才是掩码的坐标系。**

**再加一层独立验证：`0x209D` 在 exe 里只出现 1 次（`0x0F3ED0`），
在 `reg_Preferences.bin` 里也只出现 1 次（`0x0FB8`）。**
如果它是普通常量，不可能恰好只在两张列配置表头上各出现一次、
而且两份 200 字节记录 **byte-for-byte 完全相同**（我用 `Buffer.equals` 验过）。

**旁证（自洽性）**：`reg_Preferences.bin` 里只有 4 个页块
（`@0x50` 页 id=0 / `@0x3A0` id=3 / `@0x6F0` id=4 / `@0xA40` id=2），
**没有详细信息页（id=5）的块** —— 与「从没改过、一直用出厂值」完全自洽。
（页 id 1=性能、5=详细信息、6=服务 均无记录。）

### 1.4 因此，原版详细信息页默认列清单（结论）

```
名称 | PID | 状态 | 用户名 | CPU | 内存(活动的专用工作集)      —— 6 列
宽度  100    50    80      80      40        80
```

可选（选择列）另有 42 项：CPU 时间、周期、工作集、峰值工作集、工作集增量、
内存(专用/共享工作集)、提交大小、分页/非分页缓冲池、页面错误(增量)、基本优先级、
句柄、线程、用户对象、GDI 对象、I/O 读取/写入/其他(及各自字节)、路径名称、命令行、
操作系统上下文、平台、特权、UAC 虚拟化、描述、数据执行保护、
逻辑磁盘、I/O 优先级、作业对象 ID、程序包名称、企业上下文、电源节流、
硬件强制堆栈实施的保护、以及 4 个 GPU 相关项。

> **任务书里的三选一，答案是 2001–2003（实为 2001–2004 共 48 项），
> 而 2313 是进程页列族。** 「默认只显示 6–7 列」这个提示与 0x209D 的 6 个置位完全对上。

### 1.5 诚实标注的不确定点

1. **两套 48 宽度数组，数值不同**：
   - 「掩码 + 宽度」记录（`0x0F3ED8`，与注册表逐字节相同）：
     `名称 100 / 名称'100 / PID 50 / 状态 80 / 用户名 80 / 会话ID 50 / 作业对象 50 / CPU 40 / CPU时间 80 / 周期 60 / 工作集 80 / 峰值工作集 80 / 工作集增量 50 / 内存(活动) 80 / 内存(专用) 80 / 内存(共享) 80 / 提交 80 / 分页池 80 / 非分页池 80 / 页面错误 80 / 页面错误增量 40 / 基本优先级 80 / 句柄 35 / 线程 35 / 用户对象 35 / GDI 35 / …`
   - 列定义池（`0x0F4328`）：`名称 145 / 程序包名称 180 / PID 50 / 状态 100 / 用户名 80 / CPU 40 / 内存(活动) 80 / …`

   两者在 **PID=50 / 用户名=80 / CPU=40 / 内存(活动)=80** 上一致，
   在 **名称(100 vs 145) / 状态(80 vs 100)** 上不一致。
   我的判断：前者 = 页面实际保存的列宽，后者 = 「按内容自动撑开的建议宽度」
   （145 / 180 很像是 caption 测宽的结果）。
   **哪一组是首次运行的初始宽度，未证实**；但两组都远小于重实现，D-04 不变。
2. **「掩码记录第 2 个 dword = 32」的含义未证实**：exe 与注册表两处都是 32，
   而池有 48 项。可能是「允许的最大可见列数」，也可能只是版本标记。
   它不影响「6 列」这个结论（位掩码只有 6 个置位）。
3. **`内存(活动的专用工作集)` 若真宽 80px，11 个汉字列头必然截断** ——
   真实 Win10 上这个列头确实常年是截断态，但我**没有该页截图**证实，标注「未证实」。
4. 我手上**没有任何一张原版 Win10 详细信息页的截图**，全部结论来自
   exe / MUI / 注册表三方交叉。若后续拿到截图，优先核对：默认是否 6 列、
   第 6 列名字是否含「活动的」、`状态` 列是否 80/100 宽。

## 2. 逐条发现

### D-01【严重】列族选错：详细信息页用了进程页的列名表，还凭空造了「类型」列

**问题**：`kDetCols` 第一项就是「类型」，而「类型」只存在于 37xxx 列族，32xxx 列族 48 项里没有。

**依据**：
- 32xxx 列族 48 项（本文 §1.2-B）逐项读过，无「类型」。
- `0x209D` 掩码 = {名称, PID, 状态, 用户名, CPU, 内存(活动的专用工作集)}，6 位。
- `reg_Preferences.bin` 无详细信息页的页块 → 该用户跑的就是内置默认。

**重实现**：`src/tmwindow_details.cpp:30-40`

```cpp
const DetCol[] kDetCols = {
    { L"名称", 210, DT_LEFT }, { L"PID", 66, DT_RIGHT }, { L"类型", 100, DT_LEFT },
    { L"状态", 60, DT_LEFT }, { L"用户名", 180, DT_LEFT }, { L"CPU", 64, DT_RIGHT },
    { L"内存(专用工作集)", 125, DT_RIGHT }, { L"线程数", 62, DT_RIGHT },
    { L"句柄数", 62, DT_RIGHT },
};
```

**差多少**：9 列 vs 原版 6 列。多出 `类型` / `线程数` / `句柄数` 三列，
其中 `类型` 是**原版该页根本没有的维度**（不是「默认隐藏」，是「选择列里也没有」）。
少了 `内存(活动的专用工作集)`（被写成了「内存(专用工作集)」，见 D-02）。

**注意**：`GUI_DIFF.md` §八 的判断链是「`proc_header_3x.png` 有类型列 → 它是详细信息页
→ 2313 是详细信息页列名表」，方向反了（§1.2-C）。这一条不是重复报告已知差异，
而是报告「§八的结论本身是错的、因此 §八 引入的改动是错的」。

**严重度：严重。**

### D-02【明显】内存列名写错：「内存(专用工作集)」→ 原版「内存(活动的专用工作集)」

**依据**：MUI 2001 表 `id=32014 "内存(活动的专用工作集)"` 与 `id=32015 "内存(专用工作集)"`
是**两项不同的可选列**。默认可见位掩码选中是 bit13 → 池索引 13 → `32013`
→ 名字字符串 `32014 = 内存(活动的专用工作集)`。

**重实现**：`tmwindow_details.cpp:37` `{ L"内存(专用工作集)", 125, DT_RIGHT }`

**差多少**：列名少「活动的」三字；而且取值口径也不同 ——
「活动」版对应 `WorkingSetPrivateSize` 的「非挂起」子集（MUI 2089 表原文：
`由该进程所使用而其他进程无法使用的物理内存量(除挂起的 UWP 进程外)`），
「非活动」版没有那个括号限定。本项目 `collector.cpp:277` 取的是
`cur->WorkingSetPrivateSize` 全集，语义上更接近**非活动版**。
即：名字用了活动版的一半、数据用了非活动版 —— 两头不靠。

**严重度：明显。**

### D-03【严重】「选择列」/「隐藏列」菜单项存在但完全没有实现

**依据**：原版列头右键 MENU 30201 只有两项（`_probe/tm/menus_dump.txt`）：

DLGTEMPLATEEX 的 class 字段跨语言打包、我的解析器在 cdit 之后错位，未能可靠列出
控件清单，**此项标注为「对话框存在，控件清单未证实」**）。

**重实现**：`src/menus.cpp:255-259` 只 `AppendMenuW` 建了菜单项；

`src/` 里**没有任何调用点**（只有 `menus.cpp:255` 的定义）——
即列头右键菜单根本没挂上窗口。

**严重度：严重。**

### D-04【明显】6 列默认宽度全部不同，且方向互相矛盾

| 列 | 原版宽（掩码记录） | 原版宽（列定义池） | 重实现 | 差（vs 掩码记录） |
|---|---|---|---|---|
| 名称 | 100 | 145 | 210 | +110 |
| PID | 50 | 50 | 66 | +16 |
| 状态 | 80 | 100 | 60 | **−20** |
| 用户名 | 80 | 80 | 180 | **+100** |
| CPU | 40 | 40 | 64 | +24 |
| 内存 | 80 | 80 | 125 | +45 |

**依据**：`0x0F3ED8` 处 48 宽数组 + `0x0F4328` 池（§1.2-B / §1.5-1）；
重实现 `tmwindow_details.cpp:31-39`。

**为什么这是「明显」而不是「像素级」**：差的不只是数值，**方向也不一致** ——
状态列重实现**更窄**（60 vs 80），用户名列**宽了一倍多**（180 vs 80）。

### D-14【像素级】CPU / 内存数值格式：小数位语义与原版相反

else           L"%.0f%%";         // ≥1% 整数

**原版依据**（MUI 逐 ID 核对，我按 slot 展开确认）：

             id=32881/32882/32883  "KB/秒" "MB/秒" "GB/秒"

### D-15【严重】每帧对每一行调 `ResolveUser()` —— 600 行 × 每帧，用户缓存的
注释自己说 61ms/全量

`tmwindow_details.cpp:156` 在**行绘制循环内**调用 `ResolveUser(pe->pid)`。
好消息是 `usercache.cpp:15-20` 有 pid 级缓存（命中即返回），

**严重度：明显（缓存不失效）/ 像素级（域判断）。**

**一句话**：这一页不是「差几个像素」，是**做的是另一页**。
`kDetCols` 的列族来自进程页，多出的「类型」列在原版该页根本不存在，
而该页真正的 42 个可选列一个都没有、连「选择列」入口都是空的。

## 4. 修复优先级建议

1. **D-01 + D-02**：把 `kDetCols` 换成 32xxx 列族的 6 列默认集：
   `名称 / PID / 状态 / 用户名 / CPU / 内存(活动的专用工作集)`。
   同时删除「类型」「线程数」「句柄数」。
2. **D-03**：实现「选择列」对话框（48 项勾选，写回 `0x209D` 式位掩码），
   并让 `BuildHeaderContext()` 真的挂到 `WM_RBUTTONUP` 的列头分支上。
3. **D-09 + D-10 + D-06**：把这页接上进程页已有的滚动条 / 拖宽 / 排序三套基础设施 ——
   它们都已经写好了，只是被 `if (tabs_.Current() == TabId::Processes)` 挡住。
4. **D-05**：`hdrBottom` 提成一个 `DetailHeaderBottom()` 方法，绘制与两处命中共享。
5. **D-11 + D-16**：列头对齐到 `x0 + kIconLeft + kIconSize + 8`，补竖线/悬停/chevron。
